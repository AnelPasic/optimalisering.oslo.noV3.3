LeadProof will eventually own the richer cross-site inbox and attribution; its current Gate 1 does NOT accept raw personal form data.

## Minimal deliverable
1. Worker request handler and D1 schema/migrations for receipts: opaque ID, stable site identifier/validated origin, intent (`gratis-sjekk` or `pakke-bestilling`), required form inputs and allowable attribution, submission idempotency key unique *per site*, creation time, Resend notification state/attempts, future LeadProof handoff state. Preserve previous site contracts where safe; avoid duplicate status authorities.
2. **Save first, acknowledge second**. An accepted 2xx response must mean D1 has durably committed one unique canonical lead. It must NOT imply email delivery or LeadProof delivery. Database unavailable => no success; retries with same valid idempotency identity => same stored ID, conflicting content => conflict, no duplicate email. Bound transaction/claim/retry concurrency; no successful 'sent' merely because Resend returned request acknowledgement if status not appropriate.
3. Resend API key and verified sender/recipient only as server-side secrets (never browser or Git). One reviewed notification template for each intent. Avoid `undefined` on legacy absent company/contact fields; do not add unwanted UI fields back. Notifications can fail safely without losing a lead.
4. Bounded retry: scheduled or manual server-side retrier with durable attempt status, timeouts, idempotency and dead-letter/manual-review states; do not assume at-least-once sending provides guaranteed exactly-once delivery. Avoid exceeding Cloudflare Free cron counts. Design for transient Worker cancellation after save, retry/sweep on next schedule, and distinguish network uncertainty from definitive send errors.
5. Security: site/origin allowlist AND correct site binding (Origin alone is not identity); no unauthenticated admin/list/export API. Honeypot + body/schema constraints + real abuse/rate limiting, request-size/timeouts. Explicit handling for public endpoints without embedding browser secrets; no remote arbitrary origin can read stored PII. Protect any backup export via Cloudflare Access/JWT verification and scoped per-site permissions; minimal reader/export only, not a CRM. Ensure R2/Pages CMS/Git do NOT store the leads.
6. Site integration: `HomeAssessment.astro` currently hard-disabled; `AssessmentForm.astro` and `PackageOrder.astro` use separate flag-controlled transport. Adapt safely to one agreed Worker endpoint contract **without enabling real submission in review**. Keep identical UI and protected CMS content and form fields; no broken fallback/deep links. Do not change production flags as side effect.
7. Operational docs: D1 migration and bindings, single-site setup, optional shared D1 for *Medon-owned* sites only with clear tenant isolation, separate D1 for external customers when justified, Resend source/recipient, secrets, sender authorization, quotas, privacy/retention/delete/export, retries/alerts, backup/recovery and later LeadProof integration without sending raw PII to event-only Gate 1.
8. Tests: isolated synthetic DB/API unit+integration; unique idempotency, race/duplicate, bad site/Origin, invalid payload, D1 write failures, Resend failed/slow/uncertain, retry after interrupted execution, unauthorized access to admin/export, multi-site isolation. Build, browser checks for all three existing form paths at 320/390/1440px; verify **zero real POST** in noindex preview. Fix stale old phone fixtures and email template, not user-approved three-field design.
