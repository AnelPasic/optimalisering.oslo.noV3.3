Use the same semantic primitive/composition rather than approximation via an `info-item` class and unrelated legacy geometry.
2. The chosen `Kort` must work on `passer`'s actual two-column lavender section with dark/soft child surfaces, and across 2/3/4 columns and 1440/900/390/320 widths. It must work on both existing ordinary content renderers; no homepage-only cosmetic fix.

Only explicit `Kort` should request card treatment. Existing special intentionally-card compositions (e.g., `visualId`) must not break.
4. `mekanisme` steps are **not the same section** as `passer`. Preserve their numbering, original content and automatic composition. Do not change OWNER live `mekanisme` default style or force a new baseline.

When no link is stored, **do not invent a CTA/button** just to make it resemble the demonstration; equal body padding and hierarchy should still match. When a link exists, style the action through shared semantic primitives with correct accessible link behavior; no lost navigation or forced conversion behavior.

Verify actual computed style, not just CSS presence/class names. Scoped layering/removal is preferred over escalating specificity or `!important`.
7. **Design-system remains the visual truth.** Keep the OWNER-liked demo card composition, colors/spacing/look and all lower sections intact; if possible make the 2/3/4 demos consume the same shared card primitive or assert exact geometry/property parity against production `Kort`. No new duplicated one-off demo markup that can drift again.
8. Preserve the current `home.json` (including the OWNER's `passer` content and test presentation values), all section ordering/identities, pricing/calc/proof source authority, H-025 Heroes, typography/theme, launch gates. No H-024B work, arbitrary mixed singleton creation, H-022 design/approval, SEO copy change, site redesign or form activation.
