## Product decision (keep simple)

Editors must be able to keep a section and all its content/layout/media in Pages CMS while excluding it entirely from the public page. Expose a human-facing section-level control such as **"Visning på nettsiden"** with **"Synlig (standard)"** and **"Skjult – behold i CMS"**, or an equally clear boolean **"Skjul seksjonen på nettsiden"**. Use exactly ONE visibility mechanism, not draft/archive/schedule duplicates. No scheduling, global release status or new publishing engine. An absent/legacy field MUST remain visible, with no unnecessary materialization/rewrite of current saved content.

**Visibility is a section rendering decision, not CSS.** When hidden, the section must not appear in rendered HTML, client hydration/serialized state, public JSON/page source, navigational/structured-data indexes/TOC/sitemap/anchors or a public API that would leak its content. The complete original record stays saved, editable, movable and restorable in the authenticated CMS. Re-enable restores original content, IDs, SEO-safe structure and styling without rebuilding the section. Preview Worker remains globally noindex as before, but hiding a section cannot rely on that global noindex.

**Every existing ordered homepage section type should offer the same control** (selector, calculator, packages, proof, ordinary content, assessment, FAQ), excluding the separate page Hero/chrome. Protected singleton types remain non-deletable; they may be hidden if the resulting public page remains safe and useful. If a section is the target of a public CTA or internal anchor (actual home.json has `/#sjekk`, `/#priser`), validate/warn or use a specific approved fallback that cannot silently cause dead links. Do NOT rewrite authoritative package/form/proof data sources or delete protected blocks to implement hiding: hidden homepage display must not implicitly remove package data still used by pricing/service pages. Never suppress page-level mandatory H1, legal navigation, privacy obligations or other protection.

## Part 1 — feasibility/research gate for Pages CMS Add/Delete

Current `app/src/lib/home-builder.ts` `homepageBlocksSchema` requires **exactly 8 items**, exactly one each of six protected singleton types + two ordinary content IDs (`mekanisme`/`passer`); `.pages.yml` mixed block list has `min:8,max:8`. Simply raising max permits users to add duplicate protected singleton types; a superficially enabled Add button is NOT acceptable. Preserve existing eight required blocks and current UUID/anchor/source order, but allow extra **optional ordinary content sections**, preferably within the *same real ordered/co-located CMS section list* so users can add, edit, drag and safely delete. Protected original eight and singleton IDs must remain required/non-deletable.

Before implementing, inspect actual Pages CMS block-list Add/Delete capabilities and authenticated UI behavior. Verify that the editor can truly restrict addition to ordinary `content` blocks and deletion to newly optional rows while safely keeping reorder/co-located edit. If the stock editor cannot enforce it without accidentally allowing invalid protected duplicates/deletion, **STOP and document 1–2 concrete safe alternatives with their UX/cost/tradeoffs**, e.g. minimal localized CMS customization versus separate typed optional list + insertion point (less ideal). Do not fork Pages CMS, invent hooks or implement fragile save-time cleanup silently just to pass tests. A deliberately explicit approval of a larger editor customization is preferable to a broken mixed singleton list.

If safely feasible under the existing CMS, implement the narrowest supported path and prove actual CMS Create → Save → Git → native Cloudflare Build → visible Worker; Move/Reorder → Save/Worker; Hide/Unhide → Save/Worker; Delete newly optional content only → Save/Worker; restore **exact original** source/Git bytes and CMS editor state afterward. Use a unique stable UUID, anchor slug and safe default content; prevent collisions with hidden, built-in and other optional section IDs. No duplicate DOM IDs, invalid links, orphaned assets or cached stale outputs. Existing default page and owner edits must be byte-preserved after restore.

## Part 2 — safe reversible visible/hidden toggle

Implement the typed visibility field in the same source-of-truth schema/editor for all eligible homepage sections, with a backward-compatible visible default. Prefer no source-file migration. UI control should be adjacent to the section's other CMS fields, understandable in Norwegian, and visible on collapsed cards/list labels if safely possible, e.g. "Skjult" status, to avoid confusing hidden rows with deleted ones.

Main homepage rendering should omit hidden blocks altogether *while still resolving necessary protected commercial data from the source*. Use one central rendering predicate (not a separate CSS-hidden renderer for each block family); don't accidentally hide the same underlying packages/pricing authority on other URLs. Verify no rendered text/anchor/DOM/structured output from hidden sections. Preserve editing of hidden records and stable order.

On hiding sections targeted by same-page or cross-page links (notably `/#sjekk` and `/#priser` in current homepage source), do not silently ship dead anchors. Present validation errors or an explicit safe redirect strategy with provenance; do not invent different conversion actions. Protect existing form disabled status. Hide should not alter the package prices, proofs, calculator logic, hero content or CTA authority.

If visibility control on currently protected singleton sections is technically/semantically unsafe under native Pages CMS, explain exact conflicts and obtain a scoped OWNER decision before silently limiting the feature to ordinary sections. A hidden row still counts toward uniqueness, so unpublishing cannot allow a duplicate ID/singleton.
