## Correct interpretation and design decision

**"Protected" means identity and stored content cannot be accidentally removed/duplicated; it does NOT mean always published.** Keeping the current relative order of the eight originals is an acceptable low-complexity initial model **for this bounded pilot**, with new optional sections placed **before or after ANY of the eight**. Do not frame the original eight as mandatory to show publicly. Their existing content, ids, UUIDs, attributes, options and source projections are protected and editable as appropriate. Existing whole-list drag/reordering of the original eight **will no longer be available through a single mixed list** in the stock-CMS alternative: surface this tradeoff honestly to OWNER, demonstrate the proposed replacement on the real authenticated CMS and STOP for acceptance rather than imply parity. Do not add a custom CMS or pretend Pages CMS YAML supports per-row delete guards.

Use stock Pages CMS object fields with fixed identities for all eight current core blocks, and **one** typed optional content-only list for added sections. A new optional row may select a placement with a clear Norwegian dropdown, e.g. `Før Behovsvelger`, `Etter Behovsvelger`, `Før Regneeksempel`, ..., `Etter FAQ`. Placement refers to stable protected block IDs, not numeric indexes or names. For entries with the same placement, the list's native drag order determines display order. Preview or editorial help should make the final page order easy to understand. Avoid nine separate optional lists, duplicated content copies, arbitrary CSS inputs or a second Page Builder.

The original section order to preserve unless OWNER separately changes it is: `behov` → `regneeksempel` → `sjekk` → `priser` → `resultater` → `mekanisme` → `passer` → `sporsmal`. Six are special singleton types; two (`mekanisme`, `passer`) are original normal content sections but their identity/payloads are preserved in this transition. Optional content uses the existing HomeSection/ContentCard source schema and layout/surface/box/heading options, with unique stable UID and anchor identity and no copy of special singleton types.

## Simple visibility: one control per supported section

- Expose one obvious section-level choice in Pages CMS **"Visning på nettsiden"** = **"Publisert"** (default) / **"Skjult – behold i CMS"**. Legacy absent means published. Persist complete hidden content/layout/media and allow edits/re-enable with identical content. Do not materialize a "published" value in unchanged originals.
- Default visibility available for **new optional content**, the two ordinary original content sections and safely hideable protected blocks (e.g. selector, calculator, FAQ, proof after resolving its Hero projection). Other protected types may be offered if no broken link/safety issue occurs. Do not silently require all eight to render.
- Existing `/#sjekk` and `/#priser` are referenced by real Hero or other links. Do NOT allow CMS publish to create dead links. Keep these two displayed by default and either (a) disable hiding them until a safe explicit CMS link target is defined and verified, or (b) implement blocking validation for local and cross-page inbound anchors and explain how the editor resolves it. A soft warning that still deploys a broken commercial journey is insufficient. Keep legal/navigation and required H1 accessible.
- A hidden homepage proof section must also suppress homepage-only derived Hero proof, not public source data authority; if that collateral behavior is not clearly safe/approved, document and STOP for OWNER choice. Pricing/proof/form data used on other routes remain sourced from the protected content regardless of homepage visibility. The public design-system and any open page/index must not render source-backed specimens or serialized content of hidden blocks; use explicit independently reviewed samples or omit their demo while hidden.
- Hide means **NOT RENDERED** in HTML/SSR/client/metadata/search/structured output, not merely CSS hidden. Source remains stored privately in Git/CMS; Git-hosted public source access is a separate publishing/security concern. Audit all routes that project these blocks.
- Use one typed visibility predicate and insertion resolver before render, and one authoritative commercial data resolver independent of homepage display filtering. Preserve all Card, Hero, Footer, FAQ, assessment, calculator, price/case and CTA decisions.
